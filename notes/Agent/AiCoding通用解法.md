# AI Coding 通用解法 · 六阶段方法论 + 全程例题实战

> **这类题目本质上在考三件事**（不是考你会不会调 API）：
> 1. 你能不能把一个**模糊需求**拆成**可交付的工程任务**；
> 2. 你会不会**正确使用大模型加速开发**，而不是无脑生成代码；
> 3. 你有没有**生产级开发意识**：需求、设计、实现、测试、风险、演示、复盘。
>
> 你要展示的叙事只有一句：**"我用 AI 做开发助手，但整个过程由我主导，且每一步都有工程依据。"**
>
> **主缰原则**（缰绳握在谁手里——判断"你主导"还是"AI 带着你跑"的三条可操作标准）：
> - 每段 AI 生成的代码进入项目前，你必须能**一句话说清它的职责**；
> - 每次提示词，都由你**提供上下文、约束和验收标准**，而不是只抛需求；
> - AI 给出的方案，至少经过一次**人工修改或追问修正**，让代码带上你的决策痕迹。
>
> **整个过程拆成六个阶段**：
> ① 需求澄清与范围冻结 → ② Starter / 现有仓库审计 → ③ 数据、状态、工具与运行时设计 → ④ 垂直切片和 AI 任务拆分 → ⑤ 人工 Review 与自动化验证 → ⑥ 限时取舍、演示和最终交付
>
> **贯穿全程的例题**（第 0.2 节给出完整题面）："企业知识库问答 Agent"——它覆盖了 AI coding 面试最常见的题型形态（检索 + LLM 生成 + 结构化输出 + 失败兜底），第 1~6 部分每个阶段都用它演示实际怎么做。

# 第 0 部分：总览

## 0.1 通用优先级裁决（P0~P3）

遇到"做不做得完"的纠结，按这个顺序裁决：

```
P0  必做需求的主链路（哪怕实现最丑）
P1  主链路的异常兜底（非法输入、依赖失败、超时）
P2  性价比最高的 1~2 个加分项（可观测性 / mock / 结构化输出）
P3  其余加分项、UI 美化、抽象重构
```

口诀：**先通、再稳、后亮**。先跑通，再兜底，最后才亮亮点。

## 0.2 贯穿全程的例题题面

> **题目：企业知识库问答 Agent（限时 60 分钟，Python）**
>
> 你将获得一个知识库目录 `docs_kb/`，内含若干 Markdown 文档（`faq.md` 常见问题、`policy.md` 售后政策、`products.md` 产品介绍）。请实现一个命令行问答 Agent：
>
> **必做：**
> 1. 用户输入一个自然语言问题；
> 2. Agent 先从知识库中检索相关内容（检索方式不限）；
> 3. 基于检索结果生成回答，答案末尾标注引用的文档名；
> 4. 知识库中没有相关信息时，明确回答"知识库中没有相关内容"，**不允许编造**。
>
> **硬约束：**
> - 提供一个 OpenAI 兼容的 API endpoint 与 key（**限流：每分钟 20 次请求**）；
> - 语言 Python 3.10+，运行方式不限；
> - 60 分钟后需现场演示。
>
> **加分项：** 答案 JSON 结构化输出；支持多轮追问；检索质量优化。
>
> 附带的 starter 仓库结构：`docs_kb/`（三个 md 文件）、`llm_sdk.py`（官方提供的极简 LLM 调用封装）、`tests/`（空的 pytest 目录）、`README.md`。

为什么用这道题做通用例题？因为它同时包含**工具调用（检索）、LLM 生成、结构化输出（引用）、拒答边界（防编造）、限流（韧性）、加分项（取舍）**——几乎每一种 AI coding 面试题的核心技术点都在里面。你把这道题的解法流程走通，换任何题都只是"换数据、换工具、换输出格式"，方法不变。

# 第 1 部分：阶段① · 需求澄清与范围冻结

## 1.1 阶段目标

把一个模糊需求变成一份**书面、可引用、双方（你与面试官/需求方）确认过**的范围冻结单。本阶段结束的标志不是"我看懂了"，而是"范围被冻结了"——之后所有"要不要做 X"的纠结，都回到这份文件上裁决，而不是临场拍脑袋。

## 1.2 关键动作

### 动作 1：结构化读题（3~5 分钟）

完整读一遍题目，提取以下信息（直接写进 plan.md 草稿）：

- 这个系统/Agent 到底要做什么
- 输入是什么（**用户输入 / 系统输入 / 外部资源，三者分开列**）
- 输出是什么（内容 + **格式**，格式往往是隐藏评分点）
- 必做功能 vs 可选加分项
- **硬约束**：题目指定的技术栈/调用方式、API key、限流、网络限制、运行环境（**现场最容易漏看的一类**）
- 时间限制下的 MVP 是什么

你脑子里必须先形成一句话：

> 我要先做一个最小可运行的 MVP，先满足主链路，再补异常处理、测试和文档。

### 动作 2：开口确认（现场场景专属，30 秒）

读完用 30 秒向面试官复述理解并确认优先级：

> "我确认一下：这个 Agent 的输入是 X，期望输出是 Y，必做是 A 和 B，加分项是 C。我计划先做 A+B 的主链路，再做异常兜底，时间允许补 C。这个优先级您认可吗？"

一次确认同时完成三件事：纠正误读、展示需求澄清能力、让优先级获得背书。**模糊点此刻提问是最佳时机**，编码后再问显得前期没想清楚。

### 动作 3：让 AI 辅助收敛，但人工裁定（提示词 T1，附录 A）

不要直接让模型写代码。用 T1 让模型结构化解析题目，拿到回复后人工核对三件事：

1. AI 有没有**漏掉**题目里的硬性要求（对照原文逐条勾）；
2. AI 有没有**越权推断**（把加分项当必做、把必做拆没了）——T1 要求 AI 标注"题目明说 vs 推断"，推断部分必须人工确认；
3. MVP 范围是不是真的"最小"——再砍掉一项，主链路还能跑吗？能跑，说明还有该砍的东西。

### 动作 4：写下范围冻结单（提示词 T2）

写进 `docs/plan.md` 的前半部分。**"Out of Scope + 理由"是范围冻结的灵魂**：它把"我没做"转化为"我决定不做"，这是主导权最直接的书面证据。

## 1.3 【例题实战①】知识库问答 Agent 的范围冻结单

对照 0.2 的题面，60 分钟场，产出如下（这就是交付物该有的样子，可直接照此格式写）：

```markdown
# Scope Freeze（范围冻结单） · 知识库问答 Agent

## Goal
实现一个基于本地 Markdown 知识库的命令行问答 Agent：检索 → 生成 → 带引用回答，
知识库没有的内容明确拒答。核心价值：把"查文档"这个高频动作自动化，且答案可溯源。

## Input
- 用户输入：一个自然语言问题（CLI 参数），示例："退货政策是什么"
- 系统输入：API_KEY、LLM_BASE_URL、LLM_MODEL（环境变量）；MOCK_LLM 可选
- 外部资源：docs_kb/*.md（本地文件，读取失败需兜底）；LLM API（限流 20 次/分钟）

## Output
- 预期输出：答案正文 + 引用文档名列表
- 输出格式：默认人读格式（正文 + "引用：xxx"）；--json 时输出完整结构化结果
- 失败时的输出：结构化错误 {"ok": false, "error": "..."}，而非堆栈崩溃

## In Scope（本次必做）
1. 【P0】关键词检索 docs_kb 并抽取命中片段（检索方式自选：关键词计分）
2. 【P0】组装上下文 → LLM 生成 → 输出含引用
3. 【P0】无相关内容时拒答（"知识库中没有相关内容"），引用校验防编造
4. 【P1】三类兜底：空/非法输入、知识库读取失败、LLM 失败（超时/限流/断网）

## Out of Scope（明确不做 + 理由）
1. 多轮追问——理由：需要会话状态设计，60 分钟预算内性价比低于 P1 兜底，砍掉后主链路无损
2. 检索质量优化（BM25/向量）——理由：关键词检索已满足"能检索到"，质量优化是 P2；
   检索质量不足的补偿方案：在答案与 Limitations 中如实说明（防编造优先于检索精度）
3. HTTP 服务 / Web UI——理由：题目允许 CLI，形态最简、演示最稳

## Hard Constraints
- 限流 20 次/分钟 → 设计含义：LLM 调用必须带重试+指数退避，且一次问答的 LLM 调用
  次数要有上限（解析失败重试最多 1 次）；单测全程 mock，不烧配额
- 使用 starter 的 llm_sdk.py 还是自写封装：留给阶段②审计后决策
- 输出引用必须是真实命中的文档名（代码侧校验，不信模型自觉）

## Acceptance Criteria（可执行）
1. `MOCK_LLM=1 python -m src.main "退货政策是什么"` 输出非空答案且引用包含 faq.md
2. `python -m src.main "今天天气怎么样"`（知识库外问题）输出含"知识库中没有相关内容"
3. `python -m src.main ""` 返回结构化错误（ok=false），进程不崩、退出码 1
4. 临时把 docs_kb 改名 → 返回结构化错误而非 FileNotFoundError 堆栈
5. `python -m pytest -q` 全绿（全部 mock，不依赖网络）
```

注意：验收标准（3~5 条）要全部写成"给定 X 应得到 Y"的可验证形式——这不是给自己看的备忘，而是答辩时可以直接现场执行的演示脚本（第 6.3 节的演示脚本就是按它排的）。

**Gate 1 自检**：一句话复述目标 ✓；必做/加分/硬约束三条线都落了书面 ✓；Out of Scope 每条都有理由 ✓；验收标准全部可执行 ✓。

> **通用性说明**：换任何题，这几节结构不变——Goal / Input（三类分列）/ Output（含失败格式）/ In & Out of Scope（带理由）/ Hard Constraints / 可执行验收标准。变的只是内容。

# 第 2 部分：阶段② · Starter / 现有仓库审计

> 这是六阶段里最容易被跳过、又在真实工程和带 starter 的面试里最值钱的一个阶段。大厂真实工作 90% 是改存量代码，只会从零写 demo 的候选人会被贴上"工程经验不足"的标签。**无 starter 的题目，本阶段退化为 5 分钟"环境审计"**：Python 版本、依赖可装、API 连通性（打一次最小请求）、pytest 可跑——产出同样写进 plan.md。

## 2.1 阶段目标

在写第一行代码之前，搞清楚三件事：

1. **地形**：现有代码的结构、约定、依赖、可复用资产；
2. **约束**：我必须服从的既有规则（代码风格、目录约定、配置方式、测试框架）；
3. **红旗**：现有代码里的坑（过时依赖、坏味道、隐藏耦合、缺失配置），决定是绕开、修复还是上报。

## 2.2 关键动作

### 动作 1：十分钟标准审计流程（60 分钟场压缩到 5 分钟，按优先级裁剪）

```
1. 顶层扫描（1 min）
   ls 根目录 + 读 README + 读依赖清单（requirements.txt / pyproject.toml）
   → 判断：语言、框架、入口、运行方式

2. 入口与配置（1~2 min）
   找 main / app / __main__ / Makefile / .env.example
   → 判断：怎么启动、需要哪些环境变量、有没有现成的运行脚本

3. 目录结构与核心模块（1~2 min）
   src/ 下的模块划分，每个模块读文件头/类定义即可，不逐行读
   → 判断：分层方式、可复用的工具/基类

4. 测试与 CI（1 min）
   tests/ 目录、CI 配置
   → 判断：测试框架是什么、怎么跑、有没有现成 fixture/mock 可复用

5. 红旗扫描（1 min）
   git log --oneline -10（最近在改什么）、TODO/FIXME/HACK、明显的坏味道
   → 判断：哪些地方"看起来能跑但有雷"
```

### 动作 2：让 AI 当审计副驾，不当审计法官（提示词 T3）

把关键文件喂给模型做补充审计，但**审计结论必须自己验证**。要点：让 AI **标注不确定性**，你逐条到代码里验证。AI 在不熟悉的仓库里会自信地编造"这个函数被 X 调用"，照单全收就是被 AI 带着跑。

### 动作 3：写下审计笔记与红旗清单

红旗的三种处置方式是本阶段的核心决策：

- **绕开**：不碰它，自己的代码与它隔离（时间紧张时的默认选择）；
- **修复**：改动小、收益直接、且在题目范围内才修；
- **上报**（答辩时说）：明显有问题但不属于本次范围，主动指出"这里有个坑，生产环境应该先修它"——这是高阶信号。

## 2.3 【例题实战②】starter 仓库的审计笔记

审计过程：`ls` → 读 README（只说了"实现一个知识库问答 Agent"，无运行说明）→ 打开 `llm_sdk.py`（约 40 行）→ 瞥一眼 `docs_kb/`（三个文件，`policy.md` 里发现一段疑似 GBK 编码的乱码注释）→ tests/ 为空。

产出写进 plan.md：

```markdown
## Repo Audit
### 复用资产
- llm_sdk.py：官方提供的 LLM 调用封装（chat(messages, ...)）
  → 决策：**自写 src/llm_client.py 薄封装并复用 llm_sdk 的调用细节**？
  审计结论：llm_sdk 无超时、无重试、无 mock 支持（对限流 20 次/分钟的题是硬伤）
  → 最终决策：绕开，自写封装（把超时/重试/LLMError/MOCK_LLM 四件套加进去），
    调用协议照抄 llm_sdk（endpoint 格式、鉴权头），降低接入风险
- tests/ 的 pytest 目录与命名约定（test_*.py）：服从

### 必须服从的约定
- 目录：题目给了 docs_kb/ 与 tests/，新增代码放 src/ 包（不污染根目录）
- 运行环境：Python 3.10+（题目明说）

### 红旗清单
- 【红旗 1】llm_sdk.py 无超时/无重试/异常直接裸抛
  → 处置：绕开（自写封装）。理由：修它等于替出题人补库，改动面不可控
- 【红旗 2】policy.md 有一段乱码（疑似编码混杂）
  → 处置：上报。理由：检索按 utf-8 读，读到坏文件只 warning 跳过，不中断；
    答辩时主动指出"starter 数据本身有编码问题，生产应先修数据"
- 【红旗 3】README 无运行说明
  → 处置：修复。理由：属于交付范围（我的 README 会写全 How to Run），成本 0

### 接入点决策
- 新代码全部放 src/ 包：main.py / agent.py / tools.py / llm_client.py / prompts.py
- tests/ 下新增 test_smoke.py，服从既有 pytest 约定
```

**Gate 2 自检**：知道启动方式（无入口，我自建 `python -m src.main`）✓；识别复用资产（llm_sdk 的调用协议、pytest 约定）✓；三条红旗全部有处置决策 ✓；接入点确定且理由说得清 ✓。

> **通用性说明**：换任何带 starter 的题，这一节的四小节不变（复用资产 / 约定 / 红旗处置 / 接入点）。核心永远是那一句：**每条红旗落一个"绕开/修复/上报"的决策**。

# 第 3 部分：阶段③ · 数据、状态、工具与运行时设计

## 3.1 阶段目标

在编码前定死四张图：**数据怎么流、状态存在哪、外部能力怎么接、程序怎么跑**。本阶段的产出不是漂亮架构图，而是**可执行的设计决策记录（ADR）**——每条决策都能在答辩时用一句话说清"为什么这么选、放弃了什么"。

## 3.2 四个设计维度

### 维度 1：数据设计（Data）

- 核心数据实体是什么（如：任务、对话、检索结果），字段和类型；
- 数据的**流转路径**：输入 → 解析 → 中间结构 → 输出，每一跳的形态；
- **统一返回结构**（本指南反复强调的杠杆）：

```python
# 所有工具函数、Agent 步骤统一返回：
{"ok": bool, "data": ..., "error": str | None}
```

多工具返回五花八门 → 主流程堆满 if-else → 现场最常见的混乱源。统一结构是全项目代码质量的杠杆，成本 3 分钟。

- LLM 的结构化输出：如果输出是 JSON，**先定义 schema 再让模型生成，代码侧校验**，校验失败带格式纠正提示重试一次。

### 维度 2：状态设计（State）

回答三个问题：

- **状态有哪些**：会话上下文、多轮工具调用的中间结果、重试计数、用户配置；
- **状态放哪**：60 分钟场一律选最简——内存对象/函数参数传递；只有题目要求持久化才引入文件/SQLite；
- **状态生命周期**：一次请求内？跨请求？进程退出后还要吗？——绝大多数面试题的答案都是"请求内"，明确说出来就是设计能力。

Agent 场景特别注意：**多轮工具循环的状态要显式建模**（如 `steps: [...]` 列表），而不是散落在函数调用的隐式参数里。显式的 steps 既是状态，也是后面演示的"轨迹"。

### 维度 3：工具与外部能力设计（Tools）

Agent 类题目在这里做最关键的设计决策——**确定性逻辑 vs LLM 的边界**：

| 判断类型 | 应该由谁做 | 原因 | 典型例子 |
|---|---|---|---|
| 输入合法性、格式校验 | 确定性代码 | 快、准、可测 | 空输入、类型错误 |
| 路由/分发到固定分支 | 确定性代码（规则优先） | 稳定、零成本 | 命令解析、意图粗分 |
| 结构化抽取 | LLM 输出 + 代码校验 | 灵活但必须校验 | 从文本提取字段 |
| 开放式生成/推理 | LLM | 唯一合理选择 | 总结、回答、规划 |
| 数值计算、日期运算 | 确定性代码或工具 | LLM 会算错 | 算术、时区换算 |
| 事实性查询 | 工具（搜索/DB/文件） | LLM 会编造 | 查配置、查文档 |
| 结果格式化 | 确定性代码 | 格式必须稳定 | 拼装最终输出 |

一句话原则（答辩可直接说）：

> **凡是能用代码保证正确的，绝不让模型决定；凡是必须模型理解的，绝不裸信模型输出——中间加一层校验。**

涉及工具调用时，必须在本阶段定下**工具循环协议**：

```
决定是否需要工具 / 调哪个工具   （规则优先，兜底交给 LLM）
→ 调用（统一返回结构，失败不中断）
→ 观察结果写入上下文
→ 收敛判断（信息够了 / 达到 MAX_STEPS 上限）
→ 退出循环进入 LLM 生成
```

三要素缺一不可：**决策方式、失败策略、循环上限**。上限要双重设防：system prompt 里有轮数约定，代码里有 MAX_STEPS 硬编码。

同时定下 **LLM 封装的韧性要求**（写入设计，编码阶段执行）：

- 超时（默认 30s，可配置）；
- 重试（最多 2 次，指数退避 1s→2s，**仅对超时/限流类错误重试**——密钥错误重试是浪费配额）；
- 统一异常（自定义 `LLMError`）；
- **mock 开关**（环境变量 `MOCK_LLM=1` 返回固定文本）——现场网络不稳的保险丝，也让单测不烧 token；
- API key 走环境变量，缺失时启动即报清晰错误。

### 维度 4：运行时设计（Runtime）

- **进程形态**：CLI 单次运行？常驻 REPL？HTTP 服务？——选题目要求的最简形态，不自行升级；
- **依赖策略**：标准库 + 最小第三方依赖优先；**不引入 langchain 等重框架，除非题目要求**（60 分钟场手写 30 行 tool loop 比现场调通框架更稳、更可解释）；
- **可观测性**：统一用 logging（禁 print），关键步骤各一行日志；
- **配置管理**：环境变量 + 一个配置常量区（MAX_STEPS、超时、重试次数集中定义）；
- **启动与退出**：一条命令能启动（`python -m src.main`）；任何失败路径返回结构化错误而不是堆栈崩溃。

## 3.3 写成设计决策记录（ADR 简化版）

不写长文档，每条决策三行：**决策 → 理由 → 代价**。代价那一行是成熟度信号——只说好处的设计是营销，说清代价的才是工程。3~5 条足够。

## 3.4 【例题实战③】知识库问答 Agent 的设计节 + ADR

```markdown
## Design · 知识库问答 Agent

### Data（数据流转）
用户问题(str) → 检索词列表(list[str]) → 命中索引(dict[doc_name, {score, snippets}])
→ 组装后的上下文(str) → LLM 原始输出(str) → 解析校验 →
最终结果 {"ok", "answer", "citations", "steps", "error"}
- 工具层统一返回 {"ok", "data", "error"}；citations 必须是真实命中文档名的子集（代码校验）

### State（状态）
- 一次请求内的中间态：检索命中 hits、工具轨迹 steps —— 全部作为函数内局部变量传递
- 无跨请求状态（多轮追问是 Out of Scope）—— 生命周期：请求内
- 明确决策：不引入任何持久化

### Tools（边界划分，套用决策表）
- 输入校验（空/非字符串）        → 确定性代码
- "要不要检索"                  → 规则：单工具场景，规则退化为"未检索过就检索一次"
- 检索（查文档=事实性查询）      → 工具 search_kb（关键词计分 + 2-gram 兜底）
- 答案生成                      → LLM
- 引用抽取与防编造校验           → 确定性代码（正则 + 命中集合比对）
- 输出格式化                    → 确定性代码
- 工具循环三要素：决策=规则；失败=返回 ok=False 并继续主链路；上限=MAX_STEPS=5
  （单工具场景实际只跑一轮，保留循环结构是为了加分项扩展多工具/多轮）

### Runtime（运行时）
- 形态：CLI 单次运行（argparse），--json 可选结构化输出
- 依赖：requests + pytest，其余标准库；不引框架
- 日志：logging，检索与 LLM 各一行；禁 print（main 输出除外）
- LLM 韧性四件套：超时 30s / 重试 2 次指数退避（仅超时限流）/ LLMError / MOCK_LLM

### ADR
1. 决策：绕开 starter 的 llm_sdk.py，自写 src/llm_client.py
   理由：llm_sdk 无超时/重试/mock，与限流 20 次/分钟的硬约束直接冲突
   代价：多写约 30 行；调用协议照抄 llm_sdk，接口风险可控
2. 决策：检索用关键词计分 + 2-gram 兜底，不做向量/BM25
   理由：零依赖、5 分钟可实现、可解释可调试；题目允许"检索方式不限"
   代价：召回质量一般 → 补偿：片段窗口抽取 + Limitations 如实说明 + 答辩给升级路径
3. 决策：引用校验在代码侧做（citations ⊆ 命中文档名），不信模型自觉
   理由："防编造"是题目必做项；模型可能引用未命中文档，必须硬校验
   代价：格式不符要触发一次重试；上限 1 次，成本可控
4. 决策：LLM 输出不用强制 JSON，用人读格式 + 正则抽取引用
   理由：JSON 结构化是加分项（P2）；P0 先用最稳的"正文+引用行"约定
   代价：解析比 schema 校验弱 → 解析失败重试一次兜底
5. 决策：单测全部走 MOCK_LLM，不打真实 API
   理由：限流 20 次/分钟；mock 让测试确定性、零成本、可重复
   代价：mock 回复是固定文本，测不了真实生成质量 → 用验收标准 1 现场真跑一次
```

主流程时序（标注每步是确定性逻辑还是 LLM 调用）：

```
1. 接收 CLI 参数                     （确定性）
2. 校验输入（空/类型）                （确定性）
3. 工具循环：规则判定 → search_kb     （确定性，统一返回结构）
4. 组装上下文（命中片段 + 截断）       （确定性）
5. 调用 LLM                          （唯一不确定性来源，四件套保护）
6. 解析 + 引用校验，失败重试一次       （确定性）
7. 返回结构化结果（含 steps 轨迹）     （确定性）
```

**Gate 3 自检**：核心数据结构字段类型已写出 ✓；状态方案最简且明确生命周期 ✓；边界有书面划分、工具循环三要素齐 ✓；运行时形态/依赖/日志已定 ✓；5 条 ADR 每条说得出"为什么"和"代价" ✓。

> **通用性说明**：四维度 + ADR 三段式对任何题不变。Agent 题的重点会滑向 Tools（工具循环）；生成类题滑向 Data（输出 schema）；分析类题滑向 Runtime（数据规模）。骨架相同，重心不同。

# 第 4 部分：阶段④ · 垂直切片和 AI 任务拆分

## 4.1 阶段目标

把 MVP 从"一坨功能清单"重组为**若干条端到端可运行的垂直切片**，再把每片拆成可交给 AI 的小任务。本阶段结束的标志：你手里有一张按序执行的切片清单，每片都有"完成的验证方式"。

## 4.2 为什么是垂直切片，不是水平分层

水平分层的做法：先写完所有工具 → 再写完整个主流程 → 再写所有输出格式 → 最后联调。问题：**集成风险全部堆积到最后**，60 分钟场往往在最后 15 分钟才发现两层对不上，没有退路。

垂直切片的做法：每一片都**贯穿输入 → 处理 → 输出全链路**，切完立即端到端跑通。第一片最丑没关系，它是骨架；后面的片是在能跑的系统上做增量。这等于天然实现了"每写一层就验证"。

## 4.3 切片划分方法与排序原则

以"带检索工具的问答 Agent"为例（例题实战④给出完整拆分）：

1. **第一片必须是骨架切片**——最细的端到端通道，不包含任何难题；
2. 每片结束系统都可运行、可演示（哪怕功能很少）；
3. P1 韧性切片不放到最后——它是主链路的一部分，优先级高于所有 P2 加分片；
4. 每片预估时长 ≤ 编码总预算的 1/3，超了就再切。

## 4.4 片内 AI 任务拆分（提示词 T5）

拆分原则：

- **一次一个任务，不要整片打包生成**——保证每段产出可审查、可验证；
- 任务卡里写明**已存在的模块和返回结构**，防止 AI 重复造轮子或发明不一致的接口；
- 每张卡自带完成标准，做完即验证，再进下一张。

## 4.5 【例题实战④】四片切片清单 + 任务卡

```
切片 1 · 骨架（P0，约 8 min）
  范围：固定问题字符串 → llm_client.chat() → 打印结果
  文件：src/main.py / src/llm_client.py / src/prompts.py（最小版 SYSTEM）
  韧性要求在第一片就进 llm_client：超时/重试/LLMError/MOCK_LLM 四件套一次生成到位
  验证：MOCK_LLM=1 python -m src.main "测试" 输出非空；无 MOCK 时用真 key 打一次最小请求
  目的：打通 main → LLM → 输出 的最细通道；四件套是后面一切切片的依赖

切片 2 · 核心主链路（P0，约 12 min）
  范围：tools.search_kb() → agent.run 工具循环 → 组装上下文 → LLM → 输出含 steps
  文件：src/tools.py / src/agent.py / prompts.py（完整版 SYSTEM + 工具规则）
  验证：真实问题 "退货政策是什么" 端到端回答，steps 里能看到 search_kb 记录；
        知识库外问题输出拒答话术
  目的：题目要求的完整主链路

切片 3 · 韧性（P1，约 8 min）
  范围：空/非法输入校验；知识库目录缺失兜底；LLMError 兜底文案；
        引用解析失败重试一次 + 引用编造校验
  验证：验收标准 3（空输入）、4（目录改名）、LLM 故障（MOCK 里触发）各手动验一次，
        均返回结构化错误/兜底，进程不崩
  目的：主链路稳定性闭环（与验收标准一一对应）

切片 4 · 加分（P2，时间允许才做，约 7 min）
  范围：--json 结构化输出；pytest（smoke + bad case）；logging 规范化
  验证：python -m pytest -q 全绿；--json 输出可被 jq 解析
  目的：工程完成度信号
```

切片 2 的三张 AI 任务卡（实际发给 AI 的样子）：

```text
当前完成：切片 1（main → llm_client → 输出，已跑通）。
现在实现切片 2 中的以下任务，按顺序逐个生成，每次只生成一个任务：

任务 2.1：在 src/tools.py 实现 search_kb(query: str, kb_dir: str | None = None) -> dict
  - 功能：关键词计分检索 docs_kb/*.md，返回 {"ok", "data", "error"}；
    data 为 {文档名: {"score": int, "snippets": list[str]}}，snippets 为命中句子，最多 3 段
  - 查询词切分：按标点/空白切，长度 ≥2；若切分后 ≤1 个词，退化为 2-gram 滑窗
  - 失败（目录不存在/读取异常）返回 ok=False，不抛异常
任务 2.2：在 src/agent.py 实现 run(question: str) -> dict
  - 流程：输入校验 → 工具循环（MAX_STEPS=5，单工具规则：未检索过就检索一次）
    → 组装上下文 → chat() → 正则抽取"引用：[...]" → 校验 citations ⊆ 命中文档名
    → 返回 {"ok", "answer", "citations", "steps", "error"}
  - 解析失败重试一次；引用含未命中文档视为编造，走重试
任务 2.3：更新 src/prompts.py 的 SYSTEM（禁编造/引用格式/工具规则/轮数上限/安全边界）

约束：复用 src/llm_client.chat 与 LLMError，不重复实现；遵守统一返回结构；
      每任务完成标准见切片清单验证栏。
```

**Gate 4 自检**：切片 1 是端到端骨架且排最先 ✓；每片有独立验证方式 ✓；韧性切片排在加分片之前 ✓；每片时长 ≤ 编码预算 1/3 ✓。

> **通用性说明**：四片结构（骨架/核心/韧性/加分）本身高度通用。生成类题的"核心片"是生成+校验；分析类题的"核心片"是加载+计算；编排类题的核心片是双工具循环。骨架片永远是"输入→LLM→print"。

# 第 5 部分：阶段⑤ · 人工 Review 与自动化验证

## 5.1 阶段目标

建立双闸门：**每段 AI 产出过人工 review 才入仓，每个切片过自动化验证才算完成**。这个阶段的本质是向面试官证明：AI 的产出经过了一个有判断力的工程师的过滤。

## 5.2 人工 Review：八项审查清单

对每段 AI 生成的代码，按序过：

1. **职责**：能否一句话说清这个函数/类干什么？说不清 → 追问或拆开；
2. **接口**：签名是否清晰？返回是否符合统一结构？
3. **异常**：该捕获的捕获了吗？有没有吞掉不该吞的？（**注意重试范围**——密钥错误重试是浪费）
4. **硬编码**：URL/key/魔法数字——key 必须走环境变量；
5. **可测性**：是否依赖全局状态/网络？能否在测试里替身？
6. **复杂度**：一个函数干三件事 → 要求拆开；无意义的抽象 → 要求拍平；
7. **隐式行为**：AI 自作主张加的功能、默认值、重试逻辑——与 ADR 对不上的必须改；
8. **依赖面**：import 了什么？是否引入了不必要的新依赖（现场 ImportError 是最低级事故）。

不合格就追问修正（提示词 T7），关键技巧：**把发现的具体问题写进追问**，而不是只给抽象形容词——修正一次到位，且展示了你的 code review 能力（本身就是评分项）。

**红线**：粘贴前必须能读懂。答辩被问"这里 mock 是怎么实现的"而答不上来，是比写不出来更严重的减分——写不出来是能力问题，读不懂是诚信问题。

## 5.3 自动化验证：三层验证体系

### 第一层：逐片验证（编码过程中持续进行）

每片切完立即跑端到端（见 4.5 各片的验证方式）。工具函数另加单点验证：

```bash
python -c "from src.tools import search_kb; print(search_kb('退货政策'))"
```

### 第二层：失败场景构造（韧性切片的核心动作）

| 失败类型 | 构造方法 |
|---|---|
| 非法/空输入 | 改命令行参数，传空串或错误类型 |
| 工具失败 | 传不存在的知识库目录；或临时在工具函数加 `raise` |
| LLM 失败 | MOCK_LLM 模式里内置 `<FAIL>` 触发分支，或改错 key |

不必为每种失败写专门代码，手动构造即可，但**必须至少各演示一次**。断言的是统一返回结构（`ok=False` 且 `error` 非空），而不是断言抛异常。

### 第三层：pytest 测试（提示词 T11）

时间红线：**再紧也要有 smoke test，且 smoke test 里带一个 bad case**——一行 `assert result["ok"] is False`，投入 1 分钟，评分观感完全不同。

## 5.4 Review 过程留痕

答辩时被问"你怎么用 AI"，最硬的证据就是过程记录。低成本做法：

- plan.md 里保留 ADR 和切片清单的勾选状态；
- 关键的追问修正保留在终端历史/聊天记录里（"我让它统一返回结构，这是修正后的版本"）；
- README 的 Limitations 节写明已知短板——主动留痕比口头解释可信十倍。

# 第 6 部分：阶段⑥ · 限时取舍、演示和最终交付

## 6.1 阶段目标

在时间耗尽前完成三类决策：**砍什么（取舍）、怎么讲（演示）、怎么收（交付）**。前五个阶段决定下限，这个阶段决定上限——面试官对项目的最终印象基本由最后 10 分钟决定。

## 6.2 限时取舍

触发条件（满足其一即进入取舍模式）：

- 时间消耗达编码预算的 80%，还有切片未开动；
- 当前切片卡住超过 15 分钟；
- 发现设计缺陷需要回退。

取舍决策树：

```
当前切片卡住？
├── 是骨架/核心切片（P0）→ 缩范围继续：先让主路径跑通，兜底降级为"捕获异常返回固定文案"
├── 是韧性切片（P1）  → 保留最廉价的一条兜底（输入校验），其余降级进 Limitations
└── 是加分切片（P2）  → 直接砍，移入 Out of Scope，答辩时讲"为什么砍"（这本身是加分回答）

时间还剩 <10 分钟？

## 6.3 演示脚本（提前 3 分钟排练一遍，总长 3 分钟）

```

2. happy path + 拒答（75 秒，两条都过验收标准）

   - 空输入 → 结构化错误，退出码 1，进程不崩

- **API 不通** → `MOCK_LLM=1` 演示主链路，口述"真实调用已验证过，现在切 mock 演示逻辑"；
