# Redis 挂掉时的有区分降级

## 1. 先纠正一个前提：这里 Redis 不是缓存

它不存任何能重新查出来的数据，只存一样东西：**锁**。

所以 Redis 挂掉丢的不是性能，是**"防止同一件事被做两遍"的能力**。性能下降可以忍，防护能力消失必须马上做决定：继续，还是停。

## 2. 要解决的问题

OMS 要把订单、合同送去 OA 走人工审批。"提交审批"后端做三件事：检查单据状态能不能提交 → 把状态改成"评审中" → 调 OA 接口送过去。

问题出在前两步之间。用户手快点了两下，或者网络抖动让前端发了两次请求：

```
时间轴 →

请求 A：读状态 → 未评审 ✓   ┐
请求 B：读状态 → 未评审 ✓   │  两个请求在"对方写入之前"都读到了旧状态
请求 A：写状态 → 评审中     │
请求 B：写状态 → 评审中     ┘
请求 A：调用 OA → OA 里出现审批实例 1
请求 B：调用 OA → OA 里出现审批实例 2
```

结果：**同一张订单在 OA 里出现两个待审批任务。**

这不是代码写错了。两个步骤之间必然有一个时间差，只要两个请求都挤进这个缝里，状态检查就一定会同时通过。这种"检查的时候是对的，用的时候已经不对了"叫竞态条件（race condition）。靠"再检查一遍"解决不了，因为窗口永远存在。

解法是让同一张单子的请求排队，一次只放一个进去。这就是 `OaApprovalSubmissionGuard` 的职责，锁的 key 带上单据 ID，不同单据互不干扰：

```java
private static final String ORDER_LOCK_PREFIX = "oms:oa:submit:order:";

// 实际拼出来的 key 长这样：oms:oa:submit:order:12345
String lockKey = keyPrefix + documentId;
```

## 3. 全文最关键的一个区分：拿不到锁 ≠ Redis 连不上

同一段 `tryLock` 代码里有两种失败，处理方式正好相反：

| | 情况一：`tryLock` 返回 false | 情况二：抛 `RedisException` |
|---|---|---|
| 含义 | Redis 好好的，锁确实被别人占着 | 连不上 Redis，压根不知道锁的情况 |
| 说明什么 | **有一个请求正在处理这张单子** | **守卫本身不可用了** |
| 该怎么处理 | 一律拒绝。这是正常的业务冲突 | 分场景决定。这才是"降级" |

- 情况一是**正常的业务冲突**，没什么可商量的：另一个请求正在处理同一张单子，就该被挡住，回一句"订单正在提交OA，请勿重复操作"。这跟故障无关，也不需要降级。
- 情况二才是本文主题：**我不知道有没有人在同时处理这张单子，也没办法阻止别人现在开始处理。**

面对情况二只有三种选择：一律拒绝（Redis 挂多久业务停多久）、一律放行（防护完全消失）、分场景决定。第三种就是**有区分的降级**。

## 4. 判据只有两个问题

> **问题一：拒绝会挡住谁干活？**
>
> **问题二：放行最坏产生什么后果？这个后果能不能撤销？**

规则：

- 放行的最坏后果**能撤销** → **放行**（拒绝会挡住人干活，可恢复的错误比业务停摆更值得容忍）
- 放行的最坏后果**不可撤销** → **拒绝**（宁可报错，不可恢复的错误宁可让业务停一下）

注意判据是**能不能撤销**，不是"哪条链路更重要"。

## 5. 四个入口的结论

| 入口 | 谁在调用 | 拒绝的代价 | 放行的最坏后果 | 结论 |
|---|---|---|---|---|
| `acquireOrder` | 人点按钮 | 业务当场停摆 | 多一个审批实例，可作废 | 放行 |
| `acquireOrderChange` | 人点按钮 | 业务当场停摆 | 多一个审批实例，可作废 | 放行 |
| `acquireContract` | 人点按钮 | 业务当场停摆 | 多一个审批实例，可作废 | 放行 |
| `acquireCallback` | OA 系统 | 返回错误，OA 会重试，无人被挡 | **SAP 里出现重复合同，不可撤销** | 拒绝 |

**三个发起入口放行**：调用者是人，拒绝他就等于业务当场停住。放行的代价是并发时可能真产生两个审批实例，但**能撤销**——业务上把多余的那个作废掉就行，不污染外部系统。而且这套代码本来就处理过多实例的情况：回调流程里有"最新实例判定"，只有最新的审批实例才允许回写业务表，旧实例的延迟回调只保留自己的审批记录。

**回调入口必须拒绝**：调用者是 OA 系统，没有人在等，返回错误它通常会重试，拒绝几乎没代价。而放行的后果是：回调链路在审批通过后会**自动向 SAP 推送一次合同同步**，把合同建到 SAP 里（这段逻辑在合同的状态处理器里，状态回写事务提交成功后注册 SAP 同步，以独立事务执行一次推送）。两个重复回调并发通过，**SAP 里就会建出两张合同**，删起来要人协调、要走流程，**不可撤销**。

回调链路其实有一层幂等判断：

```java
boolean headerChanged = headerChanged(header, request, effectiveHeaderStatus, approvedLines, rejectedLines);
if (!headerChanged && changedLines.isEmpty()) {
    return;   // 状态没有任何变化，直接返回，什么都不做
}
```

但它只挡得住**先后到达**：第二个回调发现状态没变化，直接返回。它挡不住**并发到达**：两个回调都在对方提交事务之前读到旧状态，于是**都能通过这层幂等判断**，各自往下走，各自推一次 SAP。这跟第 2 节是同一个时间差问题，只是换到了回调链路，而回调链路没有第二道防线能兜住它。

## 6. 放行不是什么都不做，是退回第二道防线

发起前本来就要查单据状态（未评审 / 评审驳回才允许提交，评审中 / 评审通过都拒绝），这就是兜底。降级时打的日志也把这层意思写明了：降级为业务状态校验。

正常情况下第二个请求即使进了门，也会在状态检查这一步被挡下来，因为第一个请求已经把状态改成"评审中"了。并发下这个检查会漏——但漏了会怎样？

- 最好的情况：故障期间没有并发请求，一个都没漏，降级零代价。
- 最坏的情况：恰好两个请求同时到，漏掉一个，多出一个审批实例，作废掉就行。

Redis 故障是**低概率、短时间**的，"状态检查偶尔漏一次"的账算得过来。

反过来说：**没有能兜底的业务检查，或者放行的后果不可撤销，就不能放行。** 回调入口两条都不满足，所以它拒绝。

## 7. 代码怎么落地：三个技巧

**一、策略用方法参数传，集中一处判断**

```java
private LockHandle acquire(String keyPrefix, Long documentId, String documentName,
                           long waitSeconds, boolean degradeOnRedisError, String busyMessage) {
    ...
    } catch (RedisException exception) {
        if (degradeOnRedisError) {
            log.warn("Redis不可用，OA发起降级为业务状态校验，lockKey={}", lockKey, exception);
            return NO_OP_LOCK;
        }
        throw new CommonException("Redis不可用，无法处理" + documentName + "OA操作，请稍后重试", exception);
    }
}
```

四个入口调它时各自传值，发起链路传 `true`，回调链路传 `false`。哪条链路放行、哪条拒绝，看这四个方法就够了。

**二、放行时返回空锁，不返回 `null`**

降级时返回的是一个空对象 `NO_OP_LOCK`（一个什么都不做的 Lambda），而不是 `null`。

`null` 会逼调用方写 `if (lock != null)`，降级就漏进了业务代码，早晚有人忘。返回一个"用起来完全一样、什么都不做的对象"（空对象模式），调用方永远不需要知道降级发生过。

**三、用 `AutoCloseable` + try-with-resources 管释放**

`LockHandle` 实现了 `AutoCloseable`，于是业务代码这么写：

```java
try (OaApprovalSubmissionGuard.LockHandle ignored =
             submissionGuard.acquireOrder(id)) {

    validateOrderSubmission(id);
    OaOrderDto data = loadOrderOaData(id);
    // ... 组装报文、调用 OA

}   // ← 出这个花括号时 close() 自动被调用，锁自动释放
```

离开 try 块时 JVM 自动调 `close()`，正常结束和抛异常都会调。这对回调链路尤其重要：拒绝是靠抛异常实现的，手写 `unlock()` 会被异常跳过，只能等 120 秒租约过期。

全部 8 个调用点的业务代码都是一行，写业务的人不需要知道 Redis 好不好、当前是放行还是拒绝，也不需要手动解锁。**如果降级需要每个调用点加一个 `if`，这个降级迟早会漏。**

## 8. 另一个按场景区分的参数：等多久

```java
private static final long LOCK_LEASE_SECONDS = 120L;      // 锁的持有上限
private static final long SUBMIT_WAIT_SECONDS = 0L;       // 发起：不等
private static final long CALLBACK_WAIT_SECONDS = 5L;     // 回调：等 5 秒
```

| | 发起链路：等 0 秒 | 回调链路：等 5 秒 |
|---|---|---|
| 谁在等 | 一个盯着页面的人 | 没有人在等 |
| 为什么 | 直接告诉他"请勿重复操作"，比让他转 5 秒圈更好 | 没人等，让在途的请求先跑完；排队成功比失败好，因为 OA 未必重试 |

120 秒是**租约**（持有上限，程序崩了也会自动过期）。这和"等多久"是两个参数，和"要不要降级"也是**完全独立**的两个决定：等多久管的是"锁被别人占着"（第 3 节情况一），要不要降级管的是"Redis 连不上"（情况二）。分开判断，所以分开传参。

## 9. 迁移到自己的系统：判据速查

- [ ] **是不是分布式锁场景**：这段代码在用外部服务防止同一件事被做两遍吗？如果 Redis 只是加速查询、丢了能重查，直接查数据库，不需要本文这套判断。
- [ ] **分清两种故障**："资源被占用"是正常业务冲突，一律拒绝，不降级；只有"锁服务本身不可用"才做下面的判断。
- [ ] **问拒绝的代价**：谁被挡住了？他能不能自己重试？要等多久？是机器调用还是人在等？
- [ ] **问放行的代价**：最坏产生什么？能不能撤销？
- [ ] **给结论**：机器调用、失败能自动重试 → 倾向拒绝；有人被挡住且无法自助 → 倾向放行；放行后果不可撤销（写到外部系统、发消息、产生无法回收的单据）→ 必须拒绝。
- [ ] **放行前必须答出"退回哪道防线"**：那道防线在并发下会漏吗？漏了之后业务上怎么恢复、谁来恢复？答不出来就不能放行。
- [ ] **写代码的三个要求**：策略用方法参数集中一处判断；放行返回空对象而不是 `null`；用 `AutoCloseable` + try-with-resources 管理释放，业务代码里不出现手写加锁/解锁。
- [ ] **降级时至少打一条 WARN 日志**。降级是静默继续，不记日志，出问题的时候没人知道防护能力曾经消失过。

锁在事务里要把解锁推迟到事务结束，否则下一个请求会读到还没提交的旧数据，锁等于白加——详见深入篇第 8 节。
